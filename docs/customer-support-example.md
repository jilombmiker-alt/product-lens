# 教学示例：从AI客服观察到自己的方案

以下是**合成情境**，用于展示交付结构；不是飞书或其他真实产品的操作记录，没有真实截图、工具回执或用户验收。执行真实任务时必须替换为逐环节观察。

## 第一阶段：观察并反推原产品

场景假设：员工咨询一项内部操作规则，信息不足时会补充，答案不够用时会继续追问。

| 环节 | 合成输入或事件 | 合成页面反馈 | 能支持什么 | 仍不能确定 |
|---|---|---|---|---|
| J1 | 员工提问 | 系统要求补充业务类型 | 存在澄清交互 | 是否由独立Agent处理 |
| J2 | 员工补充类型 | 系统回答并显示参考文档入口 | 页面有回答与依据入口 | 是否真的检索、依据是否有效 |
| J3 | 员工表示未解决 | 系统提供反馈登记入口 | 存在继续处理入口 | 是否转人工、是否真实写入 |
| J4 | 员工提交反馈 | 页面显示记录编号 | 页面声称已登记 | 记录是否持久化、谁接手 |

实际执行还需逐张画面或真实工具观察定位，核对入口、依据、回执和结果；不能把这张合成表当事实账本。

反推示例：澄清、回答、登记是三类职责；是否为三个Agent未知。可能存在会话参数与业务记录，具体结构未知。第一阶段交付这些机制推断及补证动作，不直接宣布后台实现。

## 第二阶段：先适配，再方案，最后PRD

目标假设：我们要做单业务域、使用现有IM入口的内部支持助手。

| 原产品机制线索 | 对我们是否适配 | 方案取舍 |
|---|---|---|
| 缺参数先追问 | 可借鉴 | 一次只补齐当前任务必要参数 |
| 回答附依据入口 | 需要核对权限与时效 | 用服务端权限过滤知识，答案保留可访问出处 |
| 未解决后登记 | 适配但要补接收机制 | 写入服务返回可查记录；登记不等于问题解决 |
| 多个职责 | 不必拆多个Agent | 先用一个判断单元与确定性业务工具 |

形成方案：聊天入口 → 判断/澄清 → 授权检索或业务查询 → 答案验证 → 未解决时选择登记 → 写入回执 → 维护者跟进。工具、数据、状态和确认规则先明确，再组织为PRD。

PRD中的示例需求：回答应有可访问依据；缺参先追问；写入结果未知时先查状态；只有明确回执才能称登记成功。每条需求对应此前适配和方案条目，并定义可观察验收。
