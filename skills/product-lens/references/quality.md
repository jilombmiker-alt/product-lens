# 阶段校验、S07基线与回修提示词

## A. 通用校验提示词

你现在以审查视角核对当前阶段产物。不要因为正文完整、图已生成或上一轮标过“通过”就接受结论。校验范围仍遵循用户当前授权。

输入：任务卡、当前阶段提示词、产物版本、证据账本、需要复核的原始来源、已知缺口与用户修正。

按以下六项检查：

| 校验项 | 核对动作 | 不通过示例 |
|---|---|---|
| 试用成立 | 核对目标用户、实际运行记录、输入输出和文档对照 | 只读教程就标第一步完成；有界面截图却没有操作结果 |
| 来源 | 沿关键结论回到具体E记录及原始材料 | 引用文件名而未看图；用不存在的截图编号 |
| 覆盖 | 逐个用户环节检查操作前后证据、选择、反馈、结果及相邻过渡；核对截图逐张覆盖或真实观察记录 | 抽样看图声称全部查看；连点多步后反推中间过程；只读聊天；用文档补成真实操作 |
| 一致性 | 对照表、图、原文、项目/版本/时间与不同证据面 | 历史聊天+当前画布被拼成同一时点；字段在图中无来源 |
| 边界 | 检查事实、推断、建议、未知的类型和强度 | “可能”在后续被改成“已实现”；计划变成工具调用 |
| 可移交性 | 检查上下游输入、依赖、适用范围与验收条件 | 没有说明哪些假设尚未成立；只给一篇无证据摘要 |

逐项记录：
| 问题ID | 位置/结论ID | 当前说法 | 反证或缺口 | 影响范围 | 修正动作 | 修正后等级 | 需补证动作 |
|---|---|---|---|---|---|---|---|

然后给校验结论：
- `pass / 通过`：当前声明范围内关键结论可追溯、边界一致，可供指定下游使用。
- `conditional_pass / 带限制通过`：有效部分可继续；明确许可范围、禁止依赖的结论及未满足条件。例如可拆确认入口，但不能验收最终成片。
- `return_for_revision / 退回修正`：当前阶段关键结论受错标、不可追溯或冲突影响；先修正受影响产物，下游相关分支暂停。

执行规则：
1. 能凭现有证据修正的先修正，不把所有问题转给用户。
2. 修正后定向复查关联表格、图和交接包。不得只改一处文案，保留另一处错误。
3. 需要新材料才能判断时，给最小补证动作。补证信息不足不等于可以猜，也不等于所有无关工作都要停。
4. 在检查结果中列出实际做过的校验。没有独立审核者时称自检，不能声称独立评审；只有测试设计时称待执行。
5. 用户核对与证据校验单独记录。用户认可设计，不意味着对原产品后台推断已经证实。
6. 已授权连续处理时，根据校验结果推进；到达用户指定或本包默认的验收检查点、必要决策缺失或操作授权边界时等待。

阶段末输出固定摘要：
```text
当前阶段及产物版本：
本次校验方式与范围：
已修正的问题：
结论：通过 / 带限制通过 / 退回修正
可供下一步使用：
禁止据此断言：
未解决问题与最小补证：
用户核对状态：不要求 / 待核对 / 已核对（注明来源）
下一步：继续哪些内容，或在哪里停止及原因
```

## B. S07 / 形成拆解基线

输入：S01-S06的当前版本、阶段校验记录、原始证据和用户修正。

执行提示词：
1. 核对旅程、职责、工具、数据、资产和状态是否使用同一项目与兼容版本。
2. 对将被逆向设计依赖的关键结论逐条追溯。重复引用同一来源不会提高其证据等级。
3. 把结论分为已确认行为、合理推断、未知；建议设计单独存放，不混进As-Is事实。
4. 针对跨层冲突，先比较对象、时间、范围和版本。记录已排除的解释以及仍需验证的解释。
5. 为可以被下游使用的内容声明适用范围；对于缺失的后台实现，允许第二步架构设计在“建议设计”层面继续，不伪装成原产品确认架构。
6. 给基线分配版本。这里的“冻结”指供后续引用的稳定版本，不代表从此禁止修正。

输出：
- 本次原产品逆向拆解的一句话结论与范围。
- 原产品如何运行的机制说明：职责、输入判断输出、工具/数据/状态与交接；每条对应证据、推断依据及未确认点。
- 可供下一步做适配评估的能力清单；不在第一步替用户决定全部照搬。
- 已确认的旅程、职责和资产结果摘要，带E引用。
- 合理推断清单：依据、反证、适用边界。
- 未知与冲突清单：影响哪个下一步。
- 已修正问题及受影响产物。
- 阶段校验结论、可移交范围、用户核对状态。
- 基线版本与交接包。

完成条件：下游能分辨“可以作为约束的观察事实”“可探索的假设”和“我们需要自行设计的机制”，而不是拿到一张未经核对的全景图。

## C. 上游变更回修提示词

输入：新增/更正的原始证据或用户反馈、旧基线、依赖该基线的产物。

你需要修正受影响的结论链，不重跑所有无关阶段：
1. 保留旧S/E记录；新增修正记录，说明原内容是错标、误读、已过时还是被新证据否定。
2. 找到直接受影响的结论、旅程节点、契约字段和架构连线。
3. 将其状态设为待重验、被替代或撤回，保留原版本和原因；支持未改变的结论保持有效。
4. 沿依赖找到下游影响。上游标题改名不等于语义变化；上游事实被否定则需复核依赖它的设计理由。
5. 若原设计仍有独立理由可保留，将其重新标为建议设计，并说明理由，不再声称来自被撤回的事实。
6. 更新所有受影响产物和交接版本，执行定向校验。

输出影响清单：
| 变更来源 | 旧结论 | 新结论及等级 | 直接影响 | 下游影响 | 是否重做 | 新版本/状态 |
|---|---|---|---|---|---|---|

禁止：悄悄改写原始证据、把用户同意当作后台证明、只修改报告摘要而不修改图或契约。

## D. 文件可用性校验

按实际交付格式选择检查，不强制所有任务生成HTML或PDF。

| 层级 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 结构/引用检查 | 文件可解析、链接有目标、资源完整 | 页面实际可用 |
| 模拟交互或逻辑测试 | 指定输入与异常下逻辑符合预期 | 浏览器/账号/设备上的实际行为 |
| 实际渲染与UI检查 | 被检查的页面布局、控件和交互可用 | 未执行的生成、发布、计费流程成功 |
| 原产品端到端验证 | 指定用户任务在该次条件下完成 | 所有账号、场景和长期稳定性 |
| 用户验收 | 用户认可本次结果 | 隐藏实现、未测试的质量维度 |

浏览器或工具被策略拒绝时，不以其他访问通道规避。可修复允许范围内的文件问题，提供不同安全边界的静态材料，但必须区分该替代件验收与原交付验收。不能把“用另一种格式做完了”当作用户要求已自动变更。
