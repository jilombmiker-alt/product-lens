# 比对产物与交接契约

使用[阶段交接协议](handoff.md)。下方字段/JSON是本步专业payload，不建立重复的跨步事实源。AI先自检修正，用户再核对方向与效果；默认检查点见[总入口](../SKILL.md)。

以下ID、字段和状态均为本SOP的【建议设计】，不是原产品或Agent Blueprint的官方业务结构。可用Markdown表格实现，不必先建数据库。

## 身份与追溯

- E：第一步原始证据；C：第一步可追溯结论。沿用编号和版本，不重编。
- J：用户旅程步骤；R：目标需求；A：拟建业务Agent；U：产品界面板块。
- T：业务工具；D：上下文/资产对象；W：工作流；M：组件决策。
- BP：参考源定位，使用zip版本hash、文件、行号和命题范围。

执行与追溯链：`E/C原产品拆解 → 目标与适配决策 → J/U与职责 → T → D/状态 → W → 方案校验 → PRD中的R/AC`。设计阶段可以先给目标条目R编号便于追溯，但完整PRD在方案形成并自检之后生成。
引用参考组件：`R → M → BP`。BP只能证明参考源声明或实现了什么，不能支持原产品事实。

## 逐步骤总表（不可省略的主表）

| 字段 | 填写要求 |
|---|---|
| J / 用户目标与动作 | 起点、目标、用户实际动作；原行为和拟建行为分列 |
| U / 界面板块 | 输入控件、按钮、资产卡、进度/错误、用户可以做的决定 |
| 执行者与职责 | Agent / 普通代码 / 人；为何这样分配；谁调度它 |
| 输入 | 对象ID与版本、确认记录、权限及来自哪个上游 |
| 判断 | 确定性检查或开放判断；缺失时怎么处理 |
| T / 调用 | 模型工具/运行时函数/服务，触发条件、参数、同步/异步 |
| 观察与验证 | 具体资产、字段、状态、校验输出；谁执行验证 |
| 写回 | D对象/版本、状态、引用、生产者与消费者 |
| 继续与异常 | 用户满意/修改、生成成功/失败、余额充分/不足、继续/中断；适用才填 |
| M / 参考模块 | s编号及为何采用；不适用写普通业务代码，不强找组件 |
| 追溯 | E/C/R/BP，命题证据等级，未知和设计理由 |

## 业务 Agent 契约卡

1. A编号、名称、核心目标、对应J/U/R、与原角色的关系（原样/合并/拆分/新增）。
2. 触发者、触发条件、终止条件、上下游。
3. 六类输入分别列：必需/可选、字段/对象/版本、来源、缺失处理、证据等级。
4. 判断职责：哪些交给模型，哪些由规则强制；自动继续与用户确认条件。
5. 可调用T清单与权限；Agent只提出调用，执行服务再校验。
6. 输出：用户回复、页面组件意图、结构化字段、资产引用、状态建议、下游任务。
7. 数据读写：Agent允许提议哪些更新、谁校验并提交；不能改什么。
8. 完成判据：实际资产及验证、状态版本、所需确认、交接完整性。
9. 异常、取消、有限重试和恢复；尚未确认的问题。

独立Agent的必要性说明必填。只有名称不同但输入、权限、目标、生命周期均相同的职责，优先考虑合并或采用技能模板。

## 工具契约 T

| 类别 | 必填内容 |
|---|---|
| 身份 | ID、功能名称、真实接口是否已知、来自原产品/参考源码/我们设计 |
| 可调用性 | 模型暴露工具 / 运行时内部函数 / 外部服务 / 用户控件；调用者与宿主 |
| 前置条件 | 输入完整、权限、当前版本、必要确认、预算；哪些已获授权可复用 |
| 参数 | 业务对象及版本、资产引用、模型设置、请求ID/幂等键（适用时） |
| 返回 | 同步结果或provider_job_id、状态、产物引用、错误码、可重试性 |
| 结果检查 | 不仅返回success：资产是否存在、能否读取、是否匹配当前请求和版本 |
| 副作用 | 创建、覆盖、扣费、发送、发布；只读也需数据权限 |
| 提交 | 谁写D、写入何种状态、何时完成、提交失败如何保留已生成产物 |
| 重试 | 允许条件、次数/时间/成本预算，未知时写待定，不默认3次 |
| 中断与恢复 | 供应商是否支持取消、已请求取消与实际取消区别、恢复查询入口 |
| 追溯 | R/C/E/BP与实现状态：已接入/模拟/设计/未知 |

业务生成工具示例 `<生成视频工具>` 是功能占位名；`Workflow`、`todo_write` 等若使用真实参考名称，附对应来源，不能混成原产品官方工具名。

## 上下文与资产 D

按业务拆分：用户与权限、会话/项目配置、业务对象、知识依据、资产或业务回执、任务、确认、计费和验证结果。媒体创作可进一步拆剧本/角色/场景/分镜；客服则可拆问题/查询/反馈/解决状态，不强套媒体字段。

每个D写：字段/对象、来源域、版本、生产者、读取者、写入者、触发时机、读写权限、持久化范围、下游依赖、修改后失效范围、质量状态及证据。

重要区分：

- 对话是观察入口，不自动等于权威业务状态；明确哪个服务有权提交当前状态。
- 资产引用包含对象身份与版本；可用地址不是永久身份。URL可变、过期和权限需由资产服务管理。
- 用户确认绑定具体内容版本与操作范围；新版本是否需要再确认由需求决定，不能复用旧确认覆盖重大修改。
- 修改输入时标记受影响输出过期，保留不依赖该输入的资产。没有依赖图证据时是设计建议。
- 成功产物尚未提交时进入待对账/待提交状态；先查询已有结果，避免重新生成导致重复资产和费用。

## 工作流 W

每条边写：事件 → 守卫条件 → 执行者/调用 → 写回 → 下一状态。串行、并行、用户等待、外部任务等待分别表达。

建议最小状态按场景裁剪：`waiting_input / planning / waiting_confirm / queued / running / validating / commit_pending / completed / failed / cancel_requested / cancelled`。
`retrying`是有授权、有条件的重试；`handed_off`需下游实际接收记录。状态名字是设计选择，不直接覆盖页面里的原始状态。

| 事件 | 应规定的处理 |
|---|---|
| 参数缺失 | 列出最小缺失输入，不提交有副作用工具 |
| 用户修改 | 创建输入新版本，计算受影响依赖，局部重做并更新确认范围 |
| 工具已提交但结果未知 | 查询provider任务；结果明确前不盲重试 |
| 生成失败 | 保存错误；按错误类别、可重试性和预算决定修改/重试/停止 |
| 余额不足 | 服务端拦截提交；告知可改范围/等待充值等可用选择，不自动充值 |
| 安全拦截 | 保存原错误，不无证据解释成随机误判；使用合规修改路径 |
| 用户中断 | 停止后续派发，向支持取消的执行端请求取消，显示真实确认状态 |
| 迟到回调 | 记录结果但校验run、输入版本、取消标记；不能把旧任务完成覆盖当前结果 |
| 资产成功、状态写入失败 | 保留资产身份与请求ID，进入commit_pending并恢复提交/对账 |
| 完成门不通过 | 指明缺少哪项验收；只修对应项；超限或无法修复时保留未完成状态 |

## PRD交接

B1保存适配评估和目标清单，B2–B3保存职责、工具、数据与工作流方案，B4据此生成可评审PRD，并与方案互相引用。交接记录包含：文档路径、版本、所用基线版本、覆盖R、需求追溯表、质量状态、用户核对状态、待决策项和变更记录。字段为本SOP建议，不是原产品字段。生成或修改PRD不代表用户确认。

## 两步之间的交接扩展

保留第一步交接包原件；第二步另建消费记录。下面是结构示例，不是已经通过的项目。

```json
{

  "mapping_id": "mapping-example",
  "mode": "design",
  "upstream": {

    "artifact_version": null,
    "handoff_path": null,
    "used_claim_ids": [],
    "quality_status": null,
    "allowed_uses": [],
    "blocked_uses": []
  },
  "blueprint": {
    "source_id": null,
    "sha256": null,
    "read_scope": [],
    "runtime_verified": false
  },
  "prd": {
    "path": null,
    "version": null,
    "status": "not_generated",
    "baseline_version": null,

```

每条`component_decisions`至少包含：`id、decision、requirement_ids、step_ids、rationale、without_it、alternative、source_refs、reference_coverage、implementation_gaps`。
证据条目沿用`confirmed/inferred/proposed/unknown`，同时增加`source_domain`区分`product_evidence / blueprint_document / blueprint_code / our_design / runtime_result`。

PRD状态可用not_generated/draft/reviewable/needs_revision；用户核对状态独立记录。更新需求版本后，需要复核PRD与相关方案，不能继续消费旧版却声称一致。

B4设计完成只表明规格可交接；`runtime_verified`不能据此设为true。B5 readiness需要用户实际要求、有效方案和已满足的前置条件；空结构不能被当作通过。
